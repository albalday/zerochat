Arquitectura y Portabilidad

Descubre cómo funciona ZeroChat como aplicación web autónoma, independiente de servidor y 100% portable.

1. Arquitectura Web Estática y Backend Unificado

ZeroChat está diseñado bajo una premisa fundamental: máxima simplicidad, velocidad y control sin dependencias pesadas.

La aplicación web se sirve de forma directa y estática por HTTPS desde GitHub Pages como zerochat.html, cargando sus módulos css/ y js/ de manera transparente y sin empaquetado (bundle), acelerada mediante un Service Worker PWA con estrategia de revalidación en segundo plano que garantiza arranque instantáneo (0 ms de red) en dispositivos móviles.

Toda la interacción con el sistema local (ejecución de comandos, lectura y edición de archivos) se canaliza a través de un único ejecutable en Python: zerochat.py, que gestiona su propio entorno virtual en ./zerochat y autentica las sesiones mediante tokens diarios de seguridad.

Ventaja clave: Sin compiladores ni herramientas complejas de empaquetado. La aplicación web se sirve estáticamente y el backend local se ejecuta en cualquier equipo con un simple comando de terminal.

2. Modos de arranque: zerochat.html (Web / Android) vs. zerochat.py (Backend local)

ZeroChat está concebido para ofrecer dos experiencias complementarias según el contexto de uso: una aplicación web universal y autónoma (ideal para movilidad y uso diario sin instalación) y una estación de trabajo local (para desarrollo y control directo del sistema operativo).

A. La versión Web pura (zerochat.html)

Disponible directamente en la web (GitHub Pages) o abriendo el archivo localmente. Es una aplicación completa y autosuficiente que no requiere Python, terminal, servidores auxiliares ni instalación.

  • Orientación y optimización para Android (y dispositivos móviles): Diseñada como Progressive Web App (PWA) instalable en la pantalla de inicio desde Chrome u otros navegadores en Android. Su Service Worker con estrategia de caché revalidada en segundo plano garantiza un arranque instantáneo (0 ms de red), panel lateral táctil con backdrop, composer autoexpansible para teclado virtual y consumo mínimo de batería. No requiere Termux, root ni herramientas de terminal.
  • Conectividad multimodelo completa: Conexión directa desde el navegador con OpenAI, Anthropic Claude, Google Gemini y OpenRouter, así como servidores locales en red con CORS (Ollama, LM Studio).
  • Inferencia local privada en navegador (WebLLM / WebGPU): Descarga y ejecuta modelos de lenguaje open-source en la GPU del propio dispositivo sin enviar datos al exterior.
  • Motor RAG documental integrado: Indexación y búsqueda vectorial/léxica de PDFs y documentos con Orama, ejecutada en Web Workers y persistida en IndexedDB.
  • Modo Agente con herramientas de navegador: Ejecución de código JavaScript en sandbox seguro de navegador, generación de gráficas interactivas SVG, búsqueda en la web y lectura de páginas públicas.
  • Soberanía absoluta de datos: Historiales, ramas, adjuntos y configuraciones residen exclusivamente en el IndexedDB local de tu navegador.

B. Qué añade el Backend local (zerochat.py)

Diseñado para puestos de escritorio (Linux, macOS, Windows) donde el agente de IA necesita actuar como asistente de desarrollo sobre el sistema operativo:

  • Acceso al sistema de archivos local: Exploración de directorios, lectura de código fuente e inserción o edición atómica de archivos en el disco duro (read_file, edit_file, list_directory).
  • Ejecución de comandos del sistema: Lanzamiento de compilaciones, pruebas y comandos shell en la terminal local del equipo (execute_command).
  • Servidores MCP externos: Integración con el ecosistema Model Context Protocol (automatización de navegador con Playwright, servidores LSP de análisis estático, persistencia relacional SQLite).
  • Gestión automatizada de entorno: Auto-gestión de venv en ./zerochat, autenticación por token efímero diario y logging en tiempo real con marcas de tiempo y diagnóstico de errores.

3. Entrega Web Estática y Conexión con el Backend Local

ZeroChat se sirve de manera estática y universal a través de la web:

  • Servicio Web Universal (HTTPS): Servido directamente desde GitHub Pages (https://albalday.github.io/zerochat/zerochat.html). Toda la ejecución de interfaz, renderizado y llamadas a APIs de inferencia ocurre en el navegador con acceso a APIs modernas de persistencia como navigator.storage.persist() y almacenamiento seguro en IndexedDB.
  • Backend Local Unificado (zerochat.py): Al ejecutar python3 zerochat.py, el servidor local arranca en 127.0.0.1:6388, abre automáticamente el navegador apuntando a la aplicación web y transfiere el token de sesión diario de forma segura en el fragmento de la URL.
Desarrollo y pruebas locales automáticas: Al ejecutar python3 zerochat.py directamente dentro del repositorio clonado, el script detecta automáticamente el entorno de desarrollo y sirve la interfaz local en http://127.0.0.1:6388/zerochat.html sin necesidad de servidores auxiliares ni parámetros.

Cómo lanzar las pruebas:
  • python3 zerochat.py: Arranca el backend y abre automáticamente la interfaz local de desarrollo en el navegador.
  • python3 zerochat.py --test: Ejecuta la autocomprobación interna rápida de herramientas del sistema (lectura, listado y comandos).
  • npm test: Ejecuta la suite completa automatizada (unitarias, integración, arquitectura, infraestructura y navegador con Playwright).
  • npm run test:browser: Ejecuta exclusivamente las pruebas de interfaz visual y navegador.

4. Almacenamiento Local y Privacidad de Datos

La arquitectura de datos de ZeroChat sigue el principio de soberanía del usuario. La aplicación nunca envía historiales de conversación, credenciales ni documentos a ningún servidor centralizado de telemetría.

Capas de almacenamiento en el cliente:

  • IndexedDB (ZeroChatDB): Base de datos estructurada en el navegador donde se guardan las sesiones de chat, los mensajes, metadatos, configuraciones de perfiles de usuario y las ramas del motor RAG.
  • Almacenamiento aislado de adjuntos: Las imágenes Base64 y los documentos pesados se aíslan en almacenes específicos de IndexedDB para que el árbol de mensajes permanezca rápido, ligero y fluido.
  • Cache Storage API: Utilizada por el motor WebLLM para almacenar de forma persistente los pesos y parámetros de modelos locales de lenguaje descargados.
  • LocalStorage / Cookies de sesión (ChatStorage): Gestiona estados efímeros y preferencias de interfaz (como el tema oscuro o claro activo).

5. El Estado Canónico (ChatState)

Para evitar fugas de memoria o desincronizaciones entre componentes, ZeroChat utiliza un almacén de estado único y centralizado denominado ChatState.

Todo cambio en el ciclo de vida de la aplicación (cambio de sesión, inserción de un mensaje por streaming, progreso de inferencia o invocación de herramientas) se realiza mediante mutadores atómicos de dominio (como appendMessage, replaceMessages o saveSessionMetadata). De este modo, la interfaz se actualiza de manera reactiva y consistente en todo momento.

6. Reglas compartidas de conversación

Las respuestas nuevas y restauradas comparten componentes visuales de bloques y copia. El streaming conserva su cursor durante la generación. Los errores de conexión utilizan una vista común que escapa el mensaje recibido y la URL antes de incorporarlos al HTML.

La configuración activa se obtiene de ChatConfig. Las interfaces de perfiles y catálogo consultan al proveedor WebLLM para conocer los modelos completados, sin interpretar por separado sus metadatos almacenados.

El estado, el motor y las vistas reutilizan las reglas de message-turns.js para identificar turnos y reconocer mensajes iniciales de fecha. La eliminación de turnos comparte un algoritmo de saneamiento; ChatState conserva el bloqueo durante la generación y la actualización atómica del historial.
