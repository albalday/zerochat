Architecture & Portability

Learn how ZeroChat operates as a server-independent, fully autonomous, 100% portable web application.

1. Static Web Architecture & Unified Backend

ZeroChat is built on a fundamental premise: maximum simplicity, speed, and control without heavy dependencies.

The web application is served directly and statically over HTTPS from GitHub Pages as zerochat.html, loading modular css/ and js/ files transparently with no build or bundle step.

All local system interaction (command execution, file reading, and editing) is channeled through a single Python executable: zerochat.py, which manages its own virtual environment in ./zerochat and authenticates sessions using secure daily tokens.

Key advantage: No bundlers, compilers, or build pipelines. The web application runs statically and the local backend runs on any system with a single terminal command.

2. Static Web Delivery & Local Backend Connectivity

ZeroChat is distributed as a universal static web application:

  • Universal Web Delivery (HTTPS): Served directly from GitHub Pages (https://albalday.github.io/zerochat/zerochat.html). All interface rendering, agent execution, and inference calls happen in the browser with full access to modern web APIs like navigator.storage.persist() and private local IndexedDB storage.
  • Unified Local Backend (zerochat.py): Running python3 zerochat.py launches the local server on 127.0.0.1:6388, opens the browser pointing to the web app, and passes the daily session token securely via the URL fragment.
Local development & testing: To test local changes without relying on the deployed version, zerochat.py accepts a custom target URL via the --ui-url argument (for example, --ui-url http://localhost:8000/zerochat.html).

3. Local Storage & Data Privacy

ZeroChat's storage architecture strictly respects user data sovereignty. The application never transmits conversation history, credentials, or documents to any telemetry backend.

Client-side storage layers:

  • IndexedDB (ZeroChatDB): Structured browser database storing chat sessions, messages, metadata, user profile configurations, and local RAG branches.
  • Isolated Attachment Store: Large Base64 images and uploaded documents are isolated in dedicated IndexedDB object stores to keep the active message tree fast, responsive, and lightweight.
  • Cache Storage API: Used by WebLLM to persist downloaded local model weights and shader modules.
  • LocalStorage / Session Cookies (ChatStorage): Manages UI state and interface preferences (such as the active color theme).

4. Canonical State (ChatState)

To prevent memory leaks or state desynchronization across components, ZeroChat uses a single canonical state store: ChatState.

Every lifecycle change (switching sessions, appending streamed tokens, tracking inference progress, or executing tools) occurs through domain mutators (such as appendMessage, replaceMessages, or saveSessionMetadata). This ensures reactive, synchronized updates throughout the UI.

Shared conversation rules

New and restored responses share visual block and copy components. Streaming retains its cursor during generation. Connection errors use a common view that escapes the received message and URL before inserting them into HTML.

Active configuration comes from ChatConfig. Profile and catalog interfaces query the WebLLM provider for completed models instead of independently parsing stored metadata.

State, engine and views reuse message-turns.js rules to identify turns and recognize initial date messages. Turn removal shares a sanitization algorithm; ChatState retains the generation guard and atomic history update.
