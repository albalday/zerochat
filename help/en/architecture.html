Architecture & Portability

Learn how ZeroChat operates as a server-independent, fully autonomous, 100% portable web application.

1. The Autonomous Single-File Concept

ZeroChat is built on a fundamental premise: maximum portability without compromising advanced capabilities.

The final production build is bundled into a single distributable file called zerochat.html. This file packs the HTML structure, minified CSS compressed using Gzip level 9 in Base64, application JavaScript modules, and essential client-side libraries (including the Orama search engine).

When you open zerochat.html, an ultralight native bootstrap decompresses the payload in milliseconds using the browser's DecompressionStream API, allowing instant startup.

Key advantage: You can keep zerochat.html on a USB flash drive, on your desktop, or email it to yourself and run it in any modern browser without installing Node.js, Python, Docker, or system dependencies.

2. file:// Protocol vs Web Server Hosting

ZeroChat is engineered to run seamlessly in two deployment environments:

  • Local file:// protocol: Double-click the file in your desktop file manager. No local web server required. Requests to external APIs or local backends (like Ollama or LM Studio) are performed directly using browser fetch (with CORS enabled on the provider).
  • Static web server or GitHub Pages (HTTP/HTTPS): Hosted on standard web servers (Nginx, Apache, Caddy, Vercel, or GitHub Pages). This mode additionally benefits from full access to modern storage persistence APIs (navigator.storage.persist()) and secure context features.
Note on file:// restrictions: Certain browser engines restrict specific web APIs on the file:// origin (such as automatic self-downloading or certain Service Worker features). For maximum WebGPU or heavy RAG performance, an HTTP or HTTPS origin is recommended.

3. Local Storage & Data Privacy

ZeroChat's storage architecture strictly respects user data sovereignty. The application never transmits conversation history, credentials, or documents to any telemetry backend.

Client-side storage layers:

  • IndexedDB (ZeroChatDB): Structured browser database storing chat sessions, messages, metadata, user profile configurations, and local RAG branches.
  • Isolated Attachment Store: Large Base64 images and uploaded documents are isolated in dedicated IndexedDB object stores to keep the active message tree fast, responsive, and lightweight.
  • Cache Storage API: Used by WebLLM to persist downloaded local model weights and shader modules.
  • LocalStorage / Session Cookies (ChatStorage): Manages UI state, the Gemini Free Tier key (when configured locally), and interface preferences (such as the active color theme).

4. Canonical State (ChatState)

To prevent memory leaks or state desynchronization across components, ZeroChat uses a single canonical state store: ChatState.

Every lifecycle change (switching sessions, appending streamed tokens, tracking inference progress, or executing tools) occurs through domain mutators (such as appendMessage, replaceMessages, or saveSessionMetadata). This ensures reactive, synchronized updates throughout the UI.
