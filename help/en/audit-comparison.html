Review 3: Comparison

Which frontend suits a local LLM served separately?

Validity and method: ZeroChat data was checked in its code (9.1.0, commit a0393c3); data for the others comes from their public documentation, consulted on 4 and 12 October 2026. What their documentation does not mention is marked "not stated", not "no". Memory and performance were not measured.

1. Why the comparison changes

The 8.12.4 audit compared ZeroChat with multi-provider clients. The current goal is different: a single frontend for local models served by their own engine; the model changes with the task. So this review compares the interfaces commonly used in front of a local server, and leaves out those that only work with a remote provider.

3. Analysis

Compared with the llama.cpp interface

The minimal option: it ships with the server and there is nothing else to install. It is enough to chat and try the model, but the documentation consulted does not mention MCP or computer access. ZeroChat adds an agent, local tools, permissions, project mode and debugging on the same endpoint.

Compared with LM Studio

LM Studio combines engine and interface and, since version 0.3.17, acts as an MCP client with per-call confirmation and editable arguments. It is the closest alternative for a single user. ZeroChat does not run the model: it sits in front of any server (vLLM, SGLang, llama.cpp) and adds directory and command permission rules, subagents and the request interceptor.

Compared with Open WebUI

A server with a database designed for several users, with vector RAG and native MCP. It wins on administration, roles and semantic search. ZeroChat needs no server of its own to chat, starts without Docker and runs on Android with Termux, though without browser automation there.

Compared with Jan

A desktop application that runs GGUF models with llama.cpp and supports MCP. It is useful if you want the same application to load the model. For a 27B model served with vLLM or SGLang, it adds less than a client that just talks to the endpoint.

4. ZeroChat differentiators for this use

  • Engine independence: the same frontend works with vLLM, SGLang, llama.cpp, LM Studio or Ollama.
  • Reasoning sent back between agent steps when the server puts it in its own field.
  • Text <tool_call> as a fallback when the server does not parse calls.
  • Permissions with directory and command rules and a single-use signature on every backend call.
  • Editable interceptor to see exactly what the local model receives.

And its drawbacks: no semantic RAG, no multi-user support, and the user carries the burden of maintaining the project.

5. When to choose each

  • ZeroChat: one user, model served separately, an agent with controlled access to the computer and the need to see every request.
  • LM Studio: one application that loads the model and offers MCP with confirmation.
  • llama.cpp interface: trying the model without installing anything else.
  • Open WebUI: several users, roles or vector RAG.
  • Jan: a desktop application that runs GGUF locally.

Conclusion: MCP no longer sets anyone apart. What justifies ZeroChat for the current goal is engine independence, permission rules and request transparency.
