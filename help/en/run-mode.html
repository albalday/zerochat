Run a prompt from the command line

The interface answers on its own and the final answer goes to standard output.

1. How it works

zerochat --prompt "TEXT" (or python3 zerochat.py --prompt "TEXT") starts the local server and runs the agentic loop in a lightweight Node.js process using the local profile stored on the server (or the one you pass with --profile). When it finishes, it returns the answer and the process exits.

With --conversation ID you can continue a conversation already stored on the local server (either adding a new --prompt or resuming its last pending message), or turn on the Background execution switch at the top of the profiles selector so turns run in the background even if you close the tab.

zerochat --prompt "Summarize today's changes in this repository" > summary.txt
  • Standard output: only the model's final answer.
  • Standard error: the reason for a run without an answer and, with --run-file, the line [run] conversation_id=<id> new=true|false with the conversation it continues (new if it did not exist), so a script can follow it without querying the server. The server log is off by default; with --log on it also goes to standard error.
  • Execution: uses Node.js 22.13 or later in the background (no graphical browser required). Node downloads the interface each time from the same site as the browser and keeps a copy: without a connection it uses the last one, so with a local model it works offline from the first run on.
  • Working directory: file and command tools work in the directory you run the command from, as in a normal session.

2. Options

OptionEffect
--conversation IDContinues the conversation with that ID stored on the local server (the ID appears in the conversation’s JSON export). Can be combined with --prompt TEXT to append a new user turn or used on its own to resume the last pending message or answer.
--profile NAMEUses that profile (name or id) for this run only, without changing the saved active profile. If omitted, uses the conversation's original profile (if present) or the server's local profile; if it does not exist, the run ends with an error.
--run-file FILERuns the agent of a Markdown file (- for standard input) instead of --prompt, --conversation and --profile; meant for orchestrators and agents (details below).
--export FILESaves the conversation to FILE; the format comes from the extension: .md (Markdown), .json (session) or .html (as shown in the chat). It is also exported after a generation error.
--log on|offShows the startup banner and the server log on standard error. Defaults to off with --prompt.
--port PORTListening port; if it is in use, the run does not start. Without --port, uses a free OS-assigned port (never 6388 or ZEROCHAT_PORT). Always listens on 127.0.0.1 (no --host or ZEROCHAT_HOST) and accepts only its own runner token.

The --run-file file

It starts with a header between two --- lines, with one key: value per line, followed by two sections, each marker on its own line: <!-- system -->, the agent's manual (text right after the header without a marker is the manual too, so the file can be just the manual), and <!-- prompt -->, the task. Everything is optional except the task or conversation_id; an unknown or repeated key exits with code 4.

---
agent: reports.daily
conversation_id: reports.daily
profile: local
reasoning: medium
maxSteps: 20
timeout: 600
---
<!-- system -->
You are the daily reports agent: …
<!-- prompt -->
Write today's report.
  • Conversation, profile and limits: an existing conversation_id is continued; otherwise a new one is created under that ID. maxSteps (up to 1,000 model calls) and timeout (up to 86,400 s) stop the run with code 6 while keeping completed steps saved. disabledTools (comma-separated names) removes from this agent tools, MCP services (all their tools, without starting them) or the browser (browser_action or playwright) of the project's saved environment: it only removes, and a name that matches nothing of the run is listed in its warnings. reasoning sets the reasoning level (none, low, medium, high or xhigh; medium when omitted) over the profile's, and is kept when the conversation is resumed. The <!-- system --> section overrides the project's system data prompt for this run only, and projectMode (default false) controls whether AGENTS.md and .zerochat/state.md are injected.
  • Agent (agent): identifier <name> or <set>.<name> (lowercase letters, digits, _ or -, up to 64 characters). Fixed on creation; continuing with a different agent or without one exits with code 4.
  • Controller agent (controller: true): enables two tools for that run only, over the project's agents (never human chats or its own conversation): launch_agent (starts an agent's run-file, or an agent given inline without a file via agent, system_prompt and prompt, never another controller, independently and returns its conversation_id) and check_agents (status, token usage, full final answer up to 4,000 chars—or paged in 20,000-char blocks when querying a single agent—, optional last turn via include_turn, non-polling wait up to 240 s via wait_seconds while any of them is running, returning at once when none is and earlier when one starts waiting for an answer or fails, and on-demand cleanup via prune_keep). With project they operate in another project when the controller's rules grant R: to check, RX: to launch (the agent runs there with that folder's permissions) or RW: to prune.
  • Security: the file never carries tools, MCP services or permissions; they always come from the project's saved environment in Settings (missing environment exits with code 3).

--prompt, --conversation and --run-file are not combined with --no-browser or --keep-server, because the run executes in Node.js and ends when it returns the result.

3. Tools, requests to the user and server runs

  • Permissions in unattended runs: runs start contained by the project's RWX rules (default RWX:<project>/**: project files and simple local commands) and Settings › Permissions. Permanently denied tools return an error to the model (logging [run] Permiso denegado: … on stderr); any unapproved call—local or external MCP—pauses the run until you approve or deny it on its card. For unrestricted access in a maintenance folder, add RWX:/** under that project's Allowed directories.
  • Clean pause: on ask_user or a tool awaiting approval, the run saves the conversation in SQLite with the pending card, prints the question or tool on standard output and exits with code 5. Replies and approvals happen in the web interface, which resumes the run on the server (for agent conversations, in read-only supervision mode repeating the stored --run-file launch: profile, manual, projectMode, controller, reasoning and limits).
  • Tracking from an orchestrator: every run with --conversation, --run-file or agent keeps its state in SQLite even after completion. A ZeroChat started with --keep-server and the daily token from zerochat/login exposes focus_run via zerochat/heartbeat (status, result_text, pending, error, warnings, accumulated token usage and finished_at), waiting for changes without polling via since_rev and wait_ms.
  • “Background execution” switch in the profiles selector: available when connected to the local server for all profiles except Mirror and WebLLM. Runs each turn as an independent background process: the sidebar shows its status icon, opening the conversation displays steps as they are saved in SQLite, and you can stop it or answer needs_input. Allow once applies only to that exact call and arguments.
  • MCP services: the run starts its own local server and the enabled external MCP services, which stop when the run finishes.

4. Duration and exit codes

Without maxSteps or timeout in --run-file, the run has no time limit: it goes on until it finishes, you cancel it or you interrupt it (Ctrl+C), and the conversation is saved in SQLite after every step with tools, so the work done is not lost if it is cut off. For tasks that must repeat, schedule them outside (section 5).

CodeMeaning
0Finished: the answer is on standard output.
1Generation error, unknown profile, unavailable profile MCP service, an interface dialog asking the user for something, or a requested export that could not be written (in that last case the answer is still printed).
2The runner closed without returning a result.
3Startup failure: port in use, Node.js unavailable or, with --run-file, a folder without a saved environment.
4Invalid arguments (also outside --prompt).
5Paused waiting for the user: the ask_user question or the tool awaiting approval is on standard output.
6--run-file limit reached (maxSteps or timeout): the status is limit with the reason, the closed steps are saved and the conversation can be continued. When the timeout expires the runner is stopped and only the step in progress is lost.
7The conversation already has another run in progress (for example, two overlapping cron jobs with the same conversation_id): no second run is launched and the running one is left untouched.

5. Scheduled jobs (cron)

  • Profile and environment: save the profile while connected to the local server with the Save button (by default local, or the one passed in --profile) and ensure Node.js 22.13 or later is available. That way --prompt runs directly in the background without a graphical session or conflicts with your open browser.
  • Environment: cron starts with a minimal PATH in the home directory. Change to the working directory with cd and add to PATH the commands your MCP services need (node, npx, uvx…).
  • Result and overlaps: cron mails the output (MAILTO) and the exit code tells each case apart. With a fixed conversation_id, ZeroChat prevents overlaps with exit code 7; for fresh runs without a fixed ID, use flock.
  • Passing output to another agent: an agent with controller: true can launch workers with launch_agent (at most 8 runs at a time on the machine, counting the ones from the interface: the next launch fails until one finishes) and read their final answers directly via check_agents without temporary files. For large or persistent artifacts, write .md files in the project (or save stdout atomically with > out.tmp && mv out.tmp out.md); if another project needs to read them, grant an R: rule on that folder in Settings › Permissions.
MAILTO=user
0 7 * * * cd "$HOME/project" && PATH="$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin" flock -n /tmp/zerochat-prompt.lock zerochat --prompt "Prepare the daily report" --export "$HOME/reports/daily.html"

6. What each run needs

Before scheduling a run, check that the machine has everything it uses:

  • ZeroChat and Node.js: the local server installed and Node.js 22.13 or later on PATH (no graphical browser required).
  • Saved profile and environment: the profile named by --profile (or local) saved on the local server, with any local model server (LM Studio, Ollama, llama.cpp…) running; for --run-file, also the project environment saved in Settings.
  • MCP services: the ones used by the run must exist in ~/zerochat/services, with their dependencies installed, their credentials in their service.json and their commands (node, npx, uvx…) in the job's PATH. Those that ask for OAuth authorization must have completed it before in a windowed session.
  • Model browser: the one chosen in Settings › Browser: with Playwright MCP, the service installed from Settings › MCP; with browser_action, Node.js with Playwright and a compatible browser (see model browser).
  • Permissions: by default, unattended runs (--prompt and server runs) are restricted to the working directory and simple local commands (while honoring permanent denials). To grant access to additional folders or full maintenance access (RWX:/**) to a specific project, add it in Settings › Permissions › Allowed directories while in that project (stored per project).
  • Working directory: the command is launched from the directory the job works on.
