Run a prompt from the command line

The interface answers on its own and the final answer goes to standard output.

1. How it works

zerochat --prompt "TEXT" (or python3 zerochat.py --prompt "TEXT") starts the local server as usual and opens the interface in the browser. The page creates a new conversation, sends the prompt with your configuration in that browser (active connection profile, MCP services, settings) and, when it finishes, returns the answer and closes. Then the process exits.

zerochat --prompt "Summarize today's changes in this repository" > summary.txt
  • Standard output: only the model's final answer.
  • Standard error: the reason for a run without an answer. The server log is off by default; with --log on it also goes to standard error.
  • Conversation: it is saved in the browser like any other.
  • Working directory: file and command tools work in the directory you run the command from, as in a normal session.

2. Options

OptionEffect
--profile NAMEUses that connection profile (name or id) for this run only, without changing the saved active profile. If it does not exist, the run ends with an error.
--export FILESaves the conversation to FILE; the format comes from the extension: .md (Markdown), .json (session) or .html (as shown in the chat). It is also exported after a generation error.
--keep-pageDoes not close the page when it finishes, so you can see the conversation. The process exits anyway and the page is left disconnected from the server. Not combined with --headless.
--headlessOpens the browser without a window. See section 5.
--allow-dangerous-toolsAlso approves the tools that write or execute. See section 3.
--log on|offShows the startup banner and the server log on standard error. Defaults to off with --prompt.
--port PORTListening port; if it is in use, the run does not start. Without --port, if another open ZeroChat uses the default port, the run listens on a free port and coexists with it (in development, with the local interface, it does not start).

--prompt is not combined with --no-browser or --keep-server, because the run needs the browser and ends when it returns the result.

3. Tools and requests to the user

  • Approvals: every tool that asks for permission is allowed for that page's session. write_file, edit_file and run_command are denied unless you pass --allow-dangerous-tools. The rules you already have (allow all, workspace trust, permanent rules) apply as in the chat.
  • Questions: nobody can answer them. If the model asks with ask_user or any dialog appears, generation stops and the run ends with an error (The run needs the user).
  • MCP services: the ones you have configured and enabled are used, as in the chat.

4. Time limits and exit codes

The run is cut off after 15 minutes, or after 3 minutes without progress from the interface (each step, tool or answer fragment counts as progress).

CodeMeaning
0Finished: the answer is on standard output.
1Generation error, unknown profile, request to the user, or a requested export that could not be written (in that last case the answer is still printed).
2Time limit reached, or the browser closed without returning a result.
3Startup failure: port in use or browser that could not be opened.
4Invalid arguments (also outside --prompt).

5. Without a window (--headless)

On Linux, ZeroChat looks up the default browser (xdg-settings) and launches it with --headless on your normal profile, so it has your configuration. Windowless Firefox does not need a graphical session.

  • Browser already open: the profile is in use and the windowless browser cannot use it. The run then opens as a visible tab in the open browser, which closes when it finishes.
  • No identifiable browser: on Windows, macOS, Termux, or with Flatpak or Snap browsers, it opens the normal way.

6. Scheduled jobs (cron)

  • User: the ZeroChat configuration lives in the browser profile of the user who runs the job. If you use a dedicated user, open its browser once with a window and set up ZeroChat there.
  • No graphical session: use --headless, and keep that user's browser closed in other sessions while the job runs, because the run would try to open there as a tab.
  • Environment: cron starts with a minimal PATH in the home directory. Change to the working directory with cd and add to PATH the commands your MCP services need (node, npx, uvx…).
  • Result: cron mails the output (MAILTO); the exit code tells each case apart. flock keeps two runs from overlapping.
MAILTO=user
0 7 * * * cd "$HOME/project" && PATH="$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin" flock -n /tmp/zerochat-prompt.lock zerochat --prompt "Prepare the daily report" --headless --export "$HOME/reports/daily.html"
