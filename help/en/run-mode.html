Run a prompt from the command line

The interface answers on its own and the final answer goes to standard output.

1. How it works

zerochat --prompt "TEXT" (or python3 zerochat.py --prompt "TEXT") starts the local server and runs the agentic loop in a lightweight Node.js process using the local profile stored on the server (or the one you pass with --profile). When it finishes, it returns the answer and the process exits.

With --conversation ID you can continue a conversation already stored on the local server (either adding a new --prompt or resuming its last pending message), or turn on the Background execution switch at the top of the profiles selector so turns run in the background even if you close the tab.

zerochat --prompt "Summarize today's changes in this repository" > summary.txt
  • Standard output: only the model's final answer.
  • Standard error: the reason for a run without an answer. The server log is off by default; with --log on it also goes to standard error.
  • Execution: uses Node.js 22.13 or later in the background (no graphical browser required). Node downloads the interface each time from the same site as the browser and keeps a copy: without a connection it uses the last one, so with a local model it works offline from the first run on.
  • Working directory: file and command tools work in the directory you run the command from, as in a normal session.

2. Options

OptionEffect
--conversation IDContinues the conversation with that ID stored on the local server (see --list-conversations). Can be combined with --prompt TEXT to append a new user turn or used on its own to resume the last pending message or answer.
--profile NAMEUses that profile (name or id) for this run only, without changing the saved active profile. If omitted, uses the conversation's original profile (if present) or the server's local profile; if it does not exist, the run ends with an error.
--run-file FILEReads the request from a JSON file (- to read it from standard input) instead of --prompt, --conversation and --profile, meant for orchestrators: {"conversation_id": "...", "prompt": "...", "profile": "...", "systemDataPrompt": "...", "maxSteps": 20, "timeout": 600}, all optional except the prompt or the conversation. maxSteps (up to 1000) limits the calls to the model and timeout (up to 86400) the seconds since startup; when one is reached, the run ends with code 6 and what was done stays saved (see section 4). If conversation_id exists it is continued; otherwise the new conversation is saved under that ID. systemDataPrompt replaces the project's one for this run only. The file never carries tools, MCP services or permissions, which always come from the project: that is why the folder must have its environment saved in Settings (otherwise the run ends with code 3), and an unknown field ends with code 4.
--export FILESaves the conversation to FILE; the format comes from the extension: .md (Markdown), .json (session) or .html (as shown in the chat). It is also exported after a generation error.
--log on|offShows the startup banner and the server log on standard error. Defaults to off with --prompt.
--port PORTListening port; if it is in use, the run does not start. Without --port, if another open ZeroChat uses the default port, the run listens on a free port and coexists with it.

--prompt, --conversation and --run-file are not combined with --no-browser or --keep-server, because the run executes in Node.js and ends when it returns the result.

3. Tools, requests to the user and server runs

  • Approvals and questions with --prompt (without --conversation): unattended runs start contained by their working directory RWX rules (by default RWX:<project>/**: files inside the project and simple local commands, plus that project's rules in Settings › Permissions; calls outside that scope or permanently denied are blocked and return an error to the model). To let a specific project act as an unrestricted maintenance folder, open Settings › Permissions in that project and add RWX:/** under Allowed directories. Every blocked call leaves a [run] Permiso denegado: … line on standard error.
  • Clean pause: when the model asks with ask_user or a tool is waiting for approval, the run saves the conversation in SQLite with the pending card, prints the question (or the pending tool) on standard output and exits with code 5. Replies and approvals are always given in the web interface, which continues the conversation on the server with its profile (also the new ones from --run-file): the command line never asks or approves anything.
  • Tracking from an orchestrator: a run with --conversation or with the conversation_id of --run-file stores its state in SQLite, also when it finishes successfully. A ZeroChat started with --keep-server serves it over HTTP just like to the interface: with the daily token from zerochat/login, zerochat/heartbeat with focus_conversation_id returns in focus_run the status (running, needs_input, error, limit or completed), the final answer (result_text), what is pending (pending), the error, the denied permissions (warnings) and the finish time, and with since_rev and wait_ms it waits for the next change without polling. Without --keep-server, the server shuts down when it stops receiving heartbeats from a browser.
  • “Background execution” switch in the profiles selector: when connected to the local server, the top of the profiles panel shows the Background execution switch (available for all profiles except Mirror and WebLLM). When enabled, each turn runs as an independent background process (~/zerochat/runs/) using the active profile: the sidebar marks the conversation with a clock while running and with ? when waiting for your reply or permission; opening it shows each step as it is saved (the page checks every 2 seconds only while you have it open; you can open other conversations while it runs and it is fetched in full when you come back) and lets you stop it at any time or approve the tool / answer ask_user to resume. Allow once applies only to the call shown on the card, with those same arguments, and is not stored: if the model asks for something else when it resumes, the run pauses again to ask you.
  • MCP services: the run starts its own local server and the enabled external MCP services, which stop when the run finishes.

4. Duration and exit codes

Without maxSteps or timeout in --run-file, the run has no time limit: it goes on until it finishes, you cancel it or you interrupt it (Ctrl+C), and the conversation is saved in SQLite after every step with tools, so the work done is not lost if it is cut off. For tasks that must repeat, schedule them outside (section 5).

CodeMeaning
0Finished: the answer is on standard output.
1Generation error, unknown profile, unavailable profile MCP service, an interface dialog asking the user for something, or a requested export that could not be written (in that last case the answer is still printed).
2The runner closed without returning a result.
3Startup failure: port in use, Node.js unavailable or, with --run-file, a folder without a saved environment.
4Invalid arguments (also outside --prompt).
5Paused waiting for the user: the ask_user question or the tool awaiting approval is on standard output.
6--run-file limit reached (maxSteps or timeout): the status is limit with the reason, the closed steps are saved and the conversation can be continued. When the timeout expires the runner is stopped and only the step in progress is lost.

5. Scheduled jobs (cron)

  • Profile and environment: save the profile while connected to the local server with the Save button (by default local, or the one passed in --profile) and ensure Node.js 22.13 or later is available. That way --prompt runs directly in the background without a graphical session or conflicts with your open browser.
  • Environment: cron starts with a minimal PATH in the home directory. Change to the working directory with cd and add to PATH the commands your MCP services need (node, npx, uvx…).
  • Result: cron mails the output (MAILTO); the exit code tells each case apart. flock keeps two runs from overlapping.
  • Passing output to another agent: ask the prompt to write a .md file in the project, or save standard output atomically only on success (zerochat --prompt "..." > out.tmp && mv out.tmp out.md). If another project needs to read that summary, grant it an R: rule on that folder under Settings › Permissions › Allowed directories.
MAILTO=user
0 7 * * * cd "$HOME/project" && PATH="$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin" flock -n /tmp/zerochat-prompt.lock zerochat --prompt "Prepare the daily report" --export "$HOME/reports/daily.html"

6. What each run needs

Before scheduling a run, check that the machine has everything it uses:

  • ZeroChat and the browser: the local server installed and a browser whose profile has ZeroChat set up from the same origin (GitHub Pages or your installation), with its profiles, API keys and the encryption password if you use your own.
  • Profile: the one named by --profile, with provider, URL, model and API key. A local model server (LM Studio, Ollama…) must be running.
  • MCP services: the ones used by the run must exist in ~/zerochat/services, with their dependencies installed, their credentials in their service.json and their commands (node, npx, uvx…) in the job's PATH. Those that ask for OAuth authorization must have completed it before in a windowed session.
  • Model browser: the one chosen in Settings › Browser: with Playwright MCP, the service installed from Settings › MCP; with browser_action, Node.js with Playwright and a compatible browser (see model browser).
  • Permissions: by default, unattended runs (--prompt and server runs) are restricted to the working directory and simple local commands (while honoring permanent denials). To grant access to additional folders or full maintenance access (RWX:/**) to a specific project, add it in Settings › Permissions › Allowed directories while in that project (stored per project).
  • Working directory: the command is launched from the directory the job works on.
