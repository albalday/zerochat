1. Assessment

ZeroChat has a solid technical foundation for a supervised personal tool, with significant reservations about security and error recovery. The separation of providers, state, persistence, tools and interface is real and supported by tests. The full suite passes. However, additional checks reproduce a bypass of the development server's public-file allowlist, overly permissive token file permissions under a common configuration, and a deadlock in the browser controller.

A rewrite or enterprise infrastructure is not justified. These defects should be fixed and the credential protection model reviewed before expanding tool capabilities or presenting the product as a secure environment for sensitive information.

This result is not a certification, a code coverage measurement or a guarantee that no vulnerabilities exist. It is a cross-cutting review of code and documentation, execution of the test suite, and targeted checks of higher-risk areas.

2. Scope and method

The review covered zerochat.html, the main js/ modules, all eight py/ modules, their correspondence with zerochat.py, the service worker, distribution configuration, workflows, test runner, representative tests at every level and user guides. Particular attention went to local authentication, tool authorization, credentials, process execution, storage, RAG, providers and error recovery.

Execution environment: Linux, Node 24.18.1, Python 3.14.7, and Chromium through Playwright. CI specifies Node 22 and Python 3.12 on Ubuntu, so the environments are not identical.

Evidence types:

  • R: reproduced by running the suite or an additional controlled check.
  • C: confirmed in code/configuration; this does not imply exploitation or an observed production failure.
  • P: pending measurement; a validation recommendation, not a demonstrated defect.

Priorities: P1 fix before expanding exposure or capabilities; P2 next consolidation cycle; P3 incremental improvement. Severity expresses potential impact; priority also accounts for the intended personal use. No CVSS scores are assigned without a deployment-specific threat analysis.

The review did not make paid provider calls, conduct an external penetration test, run destructive load tests, evaluate accessibility with users, perform real GPU inference or install the product on Windows/macOS. It did not build a wheel either. No real credentials were inspected.

Strengths worth preserving

  1. Adapters normalize formats and streaming without scattering integration logic throughout the interface. Mirror mode lets users inspect requests without a provider.
  2. State, configuration and the conversation service have explicit boundaries and coordination tests.
  3. ZeroChatDB centralizes the schema and separates messages, attachments and knowledge. RagStorage handles persistence, quota estimates and export/import.
  4. Each tool declares its name and input schema, settings, execution, result format and optional view. Dependencies are injected through services, and the executor checks authorization before acting.
  5. The server requires an API token, compares secrets with compare_digest, limits HTTP bodies to 1 MiB and verifies signatures with expiration, a body hash and an atomically consumed nonce. Signing must not be confused with isolation from a compromised frontend.
  6. The JavaScript sandbox uses an iframe, worker, network restrictions and timed termination, with browser tests. Its own contract explains that this is not operating-system isolation.
  7. CI runs all five levels, and release publication validates the tag, package and tests before Trusted Publishing. These guarantees do not require a web bundling system.

5. Findings and actions

T01. Static-file allowlist bypass — medium, P1, R

Evidence: ZeroChatServerHandler.serve_static_file, ff-server.py. It checks that the resolved path stays inside the repository, but evaluates the allowlist against clean_rel, before resolving ... /js/../package.json starts with js/ and ultimately reads an unauthorized root-level file.

Reproduction: temporary local server and http.client.HTTPConnection; literal GET to /js/../package.json, without Authorization or Origin. Result: 200 and content identical to the file. A browser or fetch may normalize the path before sending it; the existing /../package.json case does not cover this vector.

Impact: unauthenticated reading of non-hidden, non-blocked files within the development repository. No escape outside that root, hidden-file access or code execution was demonstrated. Installed mode without a development root does not serve these files. Default loopback binding limits exposure.

Action and acceptance: apply the allowlist to the canonical relative path and review symlinks. Add HTTP requests without normalization covering .., valid paths, hidden files and symlinks. Reject every unauthorized target even if the input starts with js/.

T02. Daily token permissions depend on umask — high if local access is possible, P1, R/C

Evidence: get_daily_token, cc-environment.py, writes config/token.tmp and renames it without setting permissions. With umask 022, the reproduced mode is 0644. The token is reused during the day; existing tests explicitly require this. It is not a new secret for each launch.

Impact: another local user could read it if they can also traverse the parent directories. This does not assume every home directory is accessible. With the token, a client can initialize the API and obtain signing credentials; HMAC does not protect against token theft. The HMAC key does change on each launch.

Action and acceptance: create the secret with owner-only permissions, protect the directory and define suitable Windows ACLs. Correct permissions on existing files. Decide and document whether to retain daily-token convenience; calling it ephemeral is insufficient. Tests with permissive umask, an existing token and restart must check permissions and lifecycle without logging secrets.

T03. Limited protection of credentials and backups — high with access to storage/exports, P1, R/C

Evidence: profile-backup.js, getKey, keyMaterialFromPassword, cacheKeyMaterial. Default mode derives the AES-GCM key from a constant embedded in the code. A custom password is hashed using SHA-256 without salt or a work factor; derived material can be remembered in localStorage for 24 hours.

Impact: AES-GCM provides cryptographic integrity, but a publicly known encryption key provides no confidentiality against someone who obtains an encrypted copy. A weak password allows fast offline guessing. Remembered material permits decryption while accessible and does not protect against malicious same-origin JavaScript. The module comment acknowledges the embedded-key limitation, but the user experience must make it unambiguous.

Action and acceptance: explicitly distinguish default protection from password encryption; for confidentiality, use salted, cost-configurable key derivation, a versioned format and migration. Avoid persisting key-equivalent material without an informed choice. Test old/new restoration, incorrect passwords, tampering and removal of remembered key material. Do not introduce a change that makes existing backups unusable.

T04. Deadlock when browser automation fails — medium, P1, R

Evidence: PersistentBrowserSession.execute and close, dd-tools.py. execute holds a threading.Lock and calls close on EOF or exception; close tries to acquire that same non-reentrant lock.

Reproduction: the original class was extracted with AST and _ensure_running replaced by a simulated process with in-memory stdin and empty stdout. After immediate EOF, execute does not return and the lock stays held. The check ran in an isolated daemon thread, without a browser or leftover processes.

Impact: a process crash can block subsequent calls and session shutdown. In addition, readline() has no independent deadline; Playwright timeouts do not cover all process failures.

Action and acceptance: separate internal cleanup under the lock from public shutdown, or revise locking, and add an IPC deadline. Test EOF, invalid JSON, broken pipes, silent processes, concurrent shutdown and subsequent recovery.

T05. Python MCP may execute outside the venv — medium, P2, C

Evidence: _prepare_service, ee-mcp.py, uses sys.executable as pythonExecutable when the venv Python is missing. cc-environment.py allows execution to continue after venv creation fails.

Impact: this contradicts the rule requiring Python MCP processes to run exclusively in ~/zerochat/.venv. Global package installation was not demonstrated; the finding concerns the fallback execution path.

Action and acceptance: keep chat operational but report the affected MCP as unavailable when its isolated interpreter is missing. Test missing/failed venv creation and verify that global Python is not launched as a fallback.

T06. Privacy claims exceed the implementation — medium, P1, C

Evidence: the product introduction promises absolute privacy and no intermediaries; RAG help says data never leaves the device, while subsequently explaining that snippets are sent to the model. web-search.js uses Jina for search, and web-browser.js includes Jina and AllOrigins. The RAG index itself is built locally.

Impact: users may provide sensitive information under a mistaken expectation. Third parties may receive queries or URLs; RAG snippets sent to a remote provider leave the device. This does not mean all conversations use a proxy.

Action and acceptance: explain destinations for each function and add an explicit option to disallow intermediaries. Correct both languages. A test with intercepted requests should show that intermediary-free mode never contacts those domains.

T07. Partial execution limits and shared isolation boundaries — medium, P2, C/P

Evidence: dd-tools.py keeps BASH_SESSION and _BROWSER_SESSION per process, without conversation partitioning. The shell retains cwd and exported variables. communicate()/capture_output=True accumulate output before truncation. The branch executing with a different cwd uses subprocess.run(shell=True); the persistent branch does kill the process group on timeout.

Impact: two conversations using the same backend share system context. Truncating the response does not limit the memory needed to capture it. Cancelling a frontend request does not by itself demonstrate termination of remote work. Memory exhaustion was not induced and orphaned processes were not measured.

Action and acceptance: decide whether shared sessions are an intended feature and make that visible; offer a per-project reset or isolation where appropriate. Bound output during reading, standardize process-tree termination and test cancellation with dummy processes. A second conversation must have documented behavior for cwd, environment and browser state.

T08. Partial test selection is incomplete — medium, P2, R/C

Evidence: test-runner.mjs. generation references tests/unit/test_generation_controller.js, but the file is in tests/integration/. resolveGroupFiles silently filters missing paths. resolveChangedFiles generically selects only unit tests for changes such as js/chat-engine.js, js/state.js or js/rag-service.js, despite their integration tests.

Impact: a group or test:changed can pass without running relevant regressions. This does not affect the result of npm test or full CI, which discover all levels.

Action and acceptance: fix the group, reject nonexistent entries and test the impact map for core modules. Check group listings and selection by changed file.

T09. Web updates do not guarantee an atomic resource set — medium, P2, C/P

Evidence: sw.js precaches with Promise.allSettled, tolerates failures, activates through skipWaiting and updates individual resources using stale-while-revalidate.

Potential impact: partial updates or intermittent connectivity may leave a mixed resource set or an incomplete cache. An actual update failure was not reproduced here.

Action and acceptance: check complete installation before activation or verify a consistent resource manifest. Test a transition between two versions, one failed resource, two tabs and offline startup. Distinguish web caching from WebLLM model availability.

T10. Platform, performance and external-result coverage — medium, P2, C/P

Evidence: browser helpers use Chromium; workflows run on Ubuntu. Adapter and WebLLM tests do not establish real operation of every model or GPU. No corpus, concurrency or latency benchmark was produced.

Action and acceptance: define a minimum supported matrix; test installation on advertised platforms, Safari/Firefox if support is retained, a small controlled provider set, quotas and storage recovery. Record hardware, datasets and percentiles. Do not claim corpus capacity solely because an individual document may be 50 MiB.

T11. Frontend trust surface and dynamic dependencies — medium, P2, C

Evidence: the CSP in zerochat.html permits unsafe-inline, unsafe-eval and broad connections; providers-webllm.js imports code from a CDN. The session cookie is written by JS with Path=/ in cookies.js. GitHub Pages paths on the same domain share an origin; a path is not a security boundary.

Impact: compromise of the origin or application-executed code can reach client-accessible data and secrets. No XSS vulnerability was found or exploited here; these are trust boundaries, not evidence of compromise. npm audit does not rule them out.

Action and acceptance: inventory runtime dependencies, justify CSP exceptions and test gradual reductions. Consider a dedicated origin when hosting applications with different trust levels. Document that tool signatures do not defend against a compromised frontend itself.

T12. Concentrated responsibilities and documentation debt — low, P3, C

Evidence: modules exceeding 1,500–2,000 lines, a custom document parser and manually ordered scripts. The distribution description refers to a single HTML file although the web app requires js/ and css/. The RAG help metadescription mentions hybrid search, but rag-index.js builds text fields and runs weighted lexical queries with tolerance, without embeddings in that flow.

Action and acceptance: correct terminology, document parser limits and extract responsibilities only when changing specific areas. Preserve contracts and regressions; do not replace the architecture solely because of file size.

7. Repeating the review

Main commands executed:

npm test
npm audit --json
node scripts/test-runner.mjs --list

For the HTTP vector, start a test backend with ZEROCHAT_DATA_DIR set to a temporary directory, bound to loopback, without browser or venv initialization. Use http.client to send the literal path /js/../package.json; alternatively use curl --path-as-is. Compare status and content without introducing sensitive data. Stop the process afterward. For permissions, set umask 022, call get_daily_token in that temporary environment and inspect stat without displaying the value.

For the deadlock, simulate closed stdout and run execute in a controlled process/thread with a deadline; the check must not hang indefinitely while reproducing the defect. For encryption, use only a dummy value and verify decryption in default mode without a password.

The additional results do not alter the product test suite: they identify the gaps a future fix must cover. Earlier repository reports are historical and were not treated as evidence that a defect still exists.

Summary: a modular foundation supported by 666 passing tests, with 12 prioritized findings. The first fixes should address static-file access, token permissions and the browser automation deadlock.

Point-in-time audit dated 27 September 2026. Recommendations do not imply that fixes have been implemented.
