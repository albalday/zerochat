Review 1: Infrastructure and rules

What a test protects and what it does not in the 10.x series: backend in packages, permissions and execution in Node. Updated on 14 November 2026.

Scope and method

Review of version 10.16.0 on the dev branch (commit 865cbba), written against the current code following the docs/audits/AuditFull.md procedure. It replaces the review of 10.14.0 (commit bc942cf): there are 77 commits, four closed milestones (M64 to M67) and milestone M68 between the two, plus the end of M63.

Those commits were reviewed one by one against the findings of the previous review. What was fixed does not appear here as a finding: this page describes the current state, and the findings are numbered afresh. The history of the fixes is in Review 4.

Each claim states where it comes from:

  • [test] an automated test protects it;
  • [cmd] a reproducible command checks it today, but nothing prevents it from breaking;
  • [reading] code review, with no test or command;
  • [no test] a written rule that no test watches.

3. Local server security

  • Daily token, mandatory, in headers only, compared in constant time; it expires when the day changes with the server running and, on rotation, session authorizations are forgotten. [test] test_local_server.js, py/test_token.py, py/test_security.py
  • Sign-in with the system account (PAM or LogonUserW), a body of at most 4096 bytes and a 15-minute lockout after 5 failures. [test] py/test_login.py
  • CORS origins from a closed list and a POST-only API; the allowed headers are exactly the ones the interface sends. [test] test_local_server.js
  • Permission engine in the backend: a single evaluation hierarchy, directory rules that resolve symbolic links, run_command validated subcommand by subcommand and patterns compared argument by argument. [test] py/test_security.py
  • Authorization challenges are single-use, with a 10-minute TTL and bound to the project; a persistence failure does not run the tool. [test] py/test_security.py
  • Corrupt or unreadable policies: the error propagates and is never replaced by the default state. [test] py/test_security.py
  • Per-project isolation: session permissions, challenges and commands belong to their project, with a cap of 16 sessions. [test] py/test_security.py, py/test_run_command.py
  • Web transport with anti-SSRF protection on the URL and on every redirect, rejection of non-canonical numeric IPv4 hosts before resolving them, and a body bounded against compression bombs too. [test] py/test_network.py
  • HTTP body bounded to 1 MiB, with explicit exceptions for blobs and export, each with its edge tested. [test] test_local_server.js, test_backend_run_mode.js
  • JavaScript sandbox in the browser: an opaque-origin iframe with no network; the function constructor stays blocked until the asynchronous code settles. [test] browser_sandbox_security.test.js
  • Node runner: launched with the Node permission model (--permission: no disk writes or reads outside its script, no processes, workers or inspector) and an empty environment, it requires Node 22.13 and its download is capped at 4 MiB, with the download, 304, cache and network-failure branches tested. [test] py/test_server_runs.py, test_backend_run_mode.js
  • Runner credential: each run gets its own token that only allows tools/call, zerochat/run/* and its conversation, is revoked when the run ends, and is rejected by the backend on zerochat/security/* and zerochat/profiles/*. A failure inside the runner gives no access to permissions or profiles. [test] py/test_token.py
  • JavaScript sandbox on the server: execute_javascript runs in a separate Node process (zerochat/sandbox/execute), with --permission, no environment and no token, and is killed by signal when the timeout expires, also with an endless asynchronous loop. [test] py/test_sandbox.py, test_sandbox_node.js
  • Runner HTML parser (js/html-document.js): iterative traversals with a depth cap and a tag expression without backtracking, with the edge and the time tested. [test] test_html_document.js

4. Accepted risks

RiskSituation
execute_javascript in server runsInside its process the code runs in node:vm, which is not a security barrier. What contains an escape is the process: no disk, no environment and no backend credential. The context exposes neither fetch nor require, but the Node permission model does not limit the network until Node 25: code that escaped the context could open connections, with no credentials to send. [reading]
Shared origin albalday.github.ioOther pages on the same origin could read the session cookie, localStorage and IndexedDB. Accepted while that origin only publishes the project's own pages. That origin also serves runner.js, which the server downloads and runs with Node without checking its hash (M68-D6): it shares the trust already given to the interface, which has more reach, and its credential is the runner's limited one.
API keys of server profiles in clear textThey are stored in SQLite (0600) unencrypted, because unattended runs need them without intervention, and they are returned to any signed-in client. Whoever reads the account's files reads the keys.
Permissive content security policyzerochat.html declares script-src with 'unsafe-inline' and 'unsafe-eval': the defence against markup injection is the closed innerHTML list, not the CSP. [reading]
One conversation open in two tabsThere is no concurrency control: the last one to save wins. Documented in py/README.md.
Proxy key unencrypted in the browserIt only opens the proxy door; the server still requires the token and sign-in.
System account lockoutWith an attempt lockout below 5 (pam_faillock), failures from the web could lock the account. The help explains how to avoid it.
Non-local --hostIt exposes command execution to the network unencrypted; startup warns about it.
WebLLM from a CDN and web toolsThe WebLLM engine is imported from cdn.jsdelivr.net; web search and page reading go through the local server or Jina Reader.

5. Findings

There are no open findings: no rule is broken today and the suite is green. What remains are the accepted risks (section 4) and the following observations, which do not reach the threshold of a finding.

Minor observations

  • CI uses node-version: 22, the latest 22.x, not the declared minimum (22.13). No test launches the real runner with --permission: the startup tests replace Node with a script. In this review it started without errors on Node 24. [cmd]
  • The compiler detects symbols repeated across modules, but not two imports with the same alias and a different origin, nor an import that matches one of the project's own symbols. There are none today. [cmd]
  • Between packages, security and tools import each other; between modules there is no cycle. [cmd]
  • The visual evidence of a batch of tools travels marked with an internal message field that is removed when the context is assembled. There is a single path today and the mark does not reach the provider [reading]; a second path would have to remove it too.
  • Saving a conversation collects the attachments it stops using, but only among those it had before (save_conversation in py/storage/db.py). syncPendingBlobs (js/storage.js) uploads attachments right before saving, so if the save fails after uploading them, they stay on the server with no conversation using them and nothing collects them. [reading]
  • browser_action navega y hace una captura (test_local_server.js) failed in three of the last four runs of npm run test:all: Chromium answers "Unable to capture screenshot" when it coincides with the browser tests, which that command launches at the same time. It passes in npm run test:infrastructure and in six simultaneous runs of the same file. [cmd]
  • The test that compares runner.js with its build is only in the infrastructure level: a change in js/ validated with test:unit does not run it. [cmd]

6. Verdict

The backend is tidy and watched, and the Node process no longer holds the interface's credential. The changes in this series are small, come with the test that watches them, and several remove code instead of adding it (the test-only environment variables, the status list with no consumer, the symbol inventory). The reorganization of py/ into packages was done in successive moves protected by the suite, with a compiler that enforces the import pattern, rejects cycles and requires reading another module's state through a function. On the server, the runner works with a token limited to its run and the model's JavaScript runs in a separate process with no environment or credential: a failure inside either of them no longer reaches permissions or profiles. Two known risks remain: runner.js comes from GitHub Pages without a hash, accepted in M68-D6, and the sandbox process has network access, which the Node permission model does not limit until version 25.
