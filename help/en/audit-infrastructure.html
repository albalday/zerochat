Review 1: Infrastructure and rules

What a test protects and what it does not in the 10.x series: backend in packages, permissions and execution in Node. Updated on 13 November 2026.

Scope and method

Review of version 10.15.0 on the dev branch (commit ab1a340), written against the current code following the docs/audits/AuditFull.md procedure. It replaces the review of 10.14.0 (commit bc942cf): there are 62 commits and four closed milestones (M64 to M67) between the two, plus the end of M63.

Those commits were reviewed one by one against the findings of the previous review. What was fixed does not appear here as a finding: this page describes the current state, and the findings are numbered afresh. The history of the fixes is in Review 4.

Each claim states where it comes from:

  • [test] an automated test protects it;
  • [cmd] a reproducible command checks it today, but nothing prevents it from breaking;
  • [reading] code review, with no test or command;
  • [no test] a written rule that no test watches.

The Python backend, the least watched area in the previous review, now has a compiler with import rules, static analysis and tests on three systems. What remains unwatched sits in one place: the Node process that runs the agent on the server.

3. Local server security

  • Daily token, mandatory, in headers only, compared in constant time; it expires when the day changes with the server running and, on rotation, session authorizations are forgotten. [test] test_local_server.js, py/test_token.py, py/test_security.py
  • Sign-in with the system account (PAM or LogonUserW), a body of at most 4096 bytes and a 15-minute lockout after 5 failures. [test] py/test_login.py
  • CORS origins from a closed list and a POST-only API; the allowed headers are exactly the ones the interface sends. [test] test_local_server.js
  • Permission engine in the backend: a single evaluation hierarchy, directory rules that resolve symbolic links, run_command validated subcommand by subcommand and patterns compared argument by argument. [test] py/test_security.py
  • Authorization challenges are single-use, with a 10-minute TTL and bound to the project; a persistence failure does not run the tool. [test] py/test_security.py
  • Corrupt or unreadable policies: the error propagates and is never replaced by the default state. [test] py/test_security.py
  • Per-project isolation: session permissions, challenges and commands belong to their project, with a cap of 16 sessions. [test] py/test_security.py, py/test_run_command.py
  • Web transport with anti-SSRF protection on the URL and on every redirect, rejection of non-canonical numeric IPv4 hosts before resolving them, and a body bounded against compression bombs too. [test] py/test_network.py
  • HTTP body bounded to 1 MiB, with explicit exceptions for blobs and export, each with its edge tested. [test] test_local_server.js, test_backend_run_mode.js
  • JavaScript sandbox in the browser: an opaque-origin iframe with no network; the function constructor stays blocked until the asynchronous code settles. [test] browser_sandbox_security.test.js
  • Node runner: launched with the Node permission model (--permission: no disk writes or reads outside its script, no processes, workers or inspector), it requires Node 22.13 and its download is capped at 4 MiB, with the download, 304, cache and network-failure branches tested. [test] py/test_server_runs.py, test_backend_run_mode.js
  • What that permission model does not cover: the network and the API of the backend itself. The runner holds the full session token, and that token changes policies. See F-01 and F-02.

5. Findings

IdFinding and evidenceRisk and priorityProposal and test
F-01The code of execute_javascript in Node leaves the sandbox and, with the runner's token, grants itself permissions. executeInNode (js/sandbox.js) hands host-process objects to the node:vm context, and through them the code reaches process. Checked in this review with the runner under --permission: running commands directly and accessing the disk are denied, but the code reads the session token from the process arguments, calls the backend, sets the global policy to "allow all" with zerochat/security/update and then runs a command with run_command. The policy change is permanent. The tool belongs to the computation category and does not go through the permission engine, so text injected in a page the model reads during a server run is enough. test_sandbox_node.js does not test the escape.Security; highTwo pieces, the second independent of the sandbox: run the code in a separate process without the runner's token or environment, and give the runner a run credential limited to what it needs (tools/call, zerochat/run/* and its conversation), which the backend rejects on zerochat/security/* and zerochat/profiles/*. Test: with the runner's credential, changing policies or authorizing a challenge returns an error.
F-02runner.js is downloaded from GitHub Pages and run without an integrity check. The permission model and the size cap limit what it can do on disk, but not in the backend: through the same path as F-01, a runner.js altered at the origin holds the full token. The process also inherits the whole environment of whoever started the server (launch_node_runner, py/run_mode/supervisor.py). [reading]Security (supply chain); mediumThe limited credential of F-01 reduces the reach; add a runner hash published with the backend version and a minimal environment for the process. Test: a runner whose hash does not match is not run.
F-03An endless asynchronous loop in the Node sandbox is not interrupted: the node:vm timeout only covers the synchronous part. Checked: with a 500 ms timeout the call had not returned after 30 s. Only the supervisor cuts it after 180 s without progress, and the run ends with no answer.Stability; mediumThe separate process of F-01, killed by signal when the timeout expires. Test: the asynchronous loop returns the timeout error in the expected time.
F-04The lightweight HTML parser the runner uses (js/html-document.js, 10.15.0) has no bounds against hostile pages. Measured: 234 KiB of tags with an unclosed quote take 7.7 s and the time grows with the square of the size, so a page of the maximum accepted size (2 MiB by default) blocks the process for minutes; 5,000 nested elements overflow the stack. Parsing is synchronous and cannot be cancelled. It does not happen in the browser, which uses its own DOMParser.Stability; mediumA depth cap with iterative traversals and a tag expression that does not backtrack. Test: both cases at the edge, with bounded time and the truncation notice (AGENTS.md §4).
F-05Attachments are only deleted when conversations are deleted. Saving a conversation replaces its messages without checking the blobs that are no longer used (when editing, regenerating or deleting a message with an image), and a blob uploaded for a message that is never saved is left without an owner; neither py/storage/db.py nor js/storage.js collects them. Also, every deletion walks all stored messages to find which blobs are still in use. [reading]Data and disk; lowCollect unreferenced blobs when the conversation is saved, or in a pass at startup. Test: removing the only message that uses a blob deletes it on save.
F-06Six variables that change at run time (ACTIVE_HOST, ACTIVE_PORT, CONSOLE_CONTROL, RUN_SESSION, EXIT_ON_CLOSE, HEARTBEAT_INITIALIZED) are imported by name from another module. It works in zerochat.py because everything shares one namespace; as a real package, each importer would keep the initial value. py/ can be imported, but it does not behave like the artifact, and pyright analyses the semantics that is not the one executed. [cmd]Technical debt; lowRead that state through a function of the module that defines it, and make the compiler reject importing a name its module reassigns with global. Test: a case in py/test_build_backend.py.
F-07Caps with no edge test: MAX_FINISHED_JOBS (50), WEB_FETCH_MAX_REDIRECTS (5), MAX_MCP_MESSAGE_CHARS (16 MiB) and the 128 characters of method and tool name. Only the symbol inventory names them. [cmd]Rule (AGENTS.md §4); lowA case at N and N+1 for each.
F-08The symbol inventory of zerochat.py (tests/fixtures/zerochat_symbols.json, 424 names, and the compiler's --symbols option) was created to protect the moves of M64. With the moves finished, it forces editing a list every time a function is added or renamed, without catching any failure that compilation, ruff and the suite do not already catch.Technical debt; lowRemove the list and the option, or reduce it to the names the tests replace.
F-09The coordinators have shrunk but are still over a thousand lines: js/app.js 1,189 and js/mcp.js 1,116; in the backend, py/server/handler.py has 875.Technical debt; lowKeep splitting them when they are touched, as in M66.
F-10help/tools-agent.html and its translation say that calls to the local server "include authorization and a temporary single-use signature". That signature was the client call signing removed in M56. [reading]Presentation (help); lowDescribe the server's permissions and challenges, as remote-proxy.html already does.

According to the procedure, F-01 must be resolved or explicitly accepted before the next major version. The current acceptance (M65-D2) was made without knowing that the escape reaches the permission engine.

Minor observations

  • CI uses node-version: 22, the latest 22.x, not the declared minimum (22.13). No test launches the real runner with --permission: the startup tests replace Node with a script. In this review it started without errors on Node 24. [cmd]
  • The compiler detects symbols repeated across modules, but not two imports with the same alias and a different origin, nor an import that matches one of the project's own symbols. There are none today. [cmd]
  • Between packages, security and tools import each other; between modules there is no cycle. [cmd]
  • The visual evidence of a batch of tools travels marked with an internal message field that is removed when the context is assembled. There is a single path today and the mark does not reach the provider [reading]; a second path would have to remove it too.

6. Verdict

The backend is now tidy and watched; the risk sits in a single process. The fixes made after the previous review are well done: each one is small, comes with the test that would have caught it, and several take the chance to remove code instead of adding it (the test-only environment variables, the status list with no consumer, the test-runner fallback). The reorganization of py/ into packages was done in successive moves protected by the suite, with a compiler that enforces the import pattern and rejects cycles, and it left static analysis and tests on three systems. What has not been closed is the most serious item of the previous review, and the measure taken does not contain it: limiting the Node process with its permission model protects the disk, but that process holds the same credential as the interface, and that credential changes permissions. While the runner shares the full token, any failure inside it, be it the sandbox, a hostile page or an altered runner.js, amounts to the user's account.
