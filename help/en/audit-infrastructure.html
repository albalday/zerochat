Review 1: Infrastructure and rules

What a test protects and what it does not in the 10.x series: SQLite, backend permissions and execution in Node. Updated on 13 November 2026.

Scope and method

Review of version 10.14.0 on the dev branch (commit bc942cf), written from scratch against the current code and not starting from the conclusions of the previous review (9.11.0, commit 170ee03). There are 251 commits and 19 closed milestones (M44 to M62) between the two, with M63 open. It follows the procedure in docs/audits/AuditFull.md.

The 10.x series changes the scope of the infrastructure: the local server is no longer just a tool bridge. It stores profiles, conversations, attachments and permissions in SQLite, it alone decides the authorization of every tool, and it runs full agent turns in the background with a Node.js process. This review focuses on those new parts.

It includes four findings from a parallel review made with Gemini on the same commit (F-12 to F-15 and the extension of F-06), each checked in the code before being added.

Each claim states where it comes from:

  • [test] an automated test protects it;
  • [cmd] a reproducible command checks it today, but nothing prevents it from breaking;
  • [reading] code review, with no test or command;
  • [no test] a written rule that no test watches.

3. Local server security

  • Mandatory daily token, headers only, compared in constant time; it expires when the day changes even while the server runs. [test] test_local_server.js, py/test_token.py
  • Sign-in with the system account (PAM or LogonUserW), a body of at most 4096 bytes and a 15-minute lockout after 5 failures. [test] py/test_login.py
  • Closed list of CORS origins (albalday.github.io, 127.0.0.1 and localhost) and a POST-only API. [test] test_local_server.js
  • Permission engine in the backend: a single evaluation hierarchy, directory rules that resolve symbolic links, run_command validated subcommand by subcommand and patterns matched argument by argument. [test] py/test_security.py
  • Authorization challenges that are single-use, have a 10-minute TTL and are bound to the project; a persistence failure does not run the tool. [test] py/test_security.py
  • Corrupt or unreadable policies: the error propagates and is never replaced by the default state. [test] py/test_security.py
  • Isolation by project: session permissions, challenges and commands belong to their project, capped at 16 sessions. [test] py/test_security.py, py/test_run_command.py
  • Web transport with anti-SSRF protection on the URL and on every redirect, and a body cap that also holds against compression bombs. [test] py/test_network.py
  • HTTP body capped at 1 MiB, with explicit exceptions for blobs and export, each tested at its edge. [test] test_local_server.js, test_backend_run_mode.js
  • JavaScript sandbox in the browser: an opaque-origin iframe with no network. [test] browser_sandbox_security.test.js
  • JavaScript sandbox in Node (server runs): it does not isolate; see F-01 and F-02.
  • Node runner: downloaded from GitHub Pages and executed with no integrity check; see F-03.
  • Token rotation with the server running: the token changes, but permissions granted "for this session" stay valid; see F-12.

4. Accepted risks

RiskSituation
Shared origin albalday.github.ioOther pages on the same origin could read the session cookie, localStorage and IndexedDB. Accepted while that origin only publishes the project's own pages. Since 10.8 that origin also serves the code the server runs with Node (F-03), so the risk weighs more than before.
Server profile API keys in clear textThey are stored unencrypted in SQLite (0600), because unattended runs need them without intervention, and they are returned to any signed-in client. Whoever reads the account's files reads the keys.
Permissive content security policyzerochat.html declares script-src with 'unsafe-inline' and 'unsafe-eval': the defence against markup injection is the closed list of innerHTML uses, not the CSP. [reading]
One conversation open in two tabsThere is no concurrency control: the last one to save wins. Documented in py/README.md.
Proxy key unencrypted in the browserIt only opens the proxy door; the server still demands the token and sign-in.
System account lockoutWith an attempt lockout below 5 (pam_faillock), failures from the web could lock the account. The help explains how to avoid it.
Non-local --hostIt exposes command execution to the network unencrypted; startup warns about it.
WebLLM from a CDN and web toolsThe WebLLM engine is imported from cdn.jsdelivr.net; web search and reading go through the local server or Jina Reader.

5. Findings

IdFinding and evidenceRisk and priorityProposal and test
F-01execute_javascript in Node does not isolate the code. executeInNode (js/sandbox.js) hands the node:vm context objects from the host process (Object, Math, the console…); through them the code reaches the host's function constructor and, with it, process. Verified in this review: sandboxed code obtained the PID and the working directory of the process and ran a system command. The tool belongs to the computation category and does not go through the permission engine, so in a server run, or with --prompt without --allow-dangerous-tools, the model, or text injected into a page it reads, can run commands that bypass the policies. test_sandbox_node.js tests only one variant of the escape.Security; highRun the code in a Node child process with the permission model (--permission, no disk, processes or workers) and kill it when the deadline passes; meanwhile, remove the tool from the runner. Test: escapes through inherited objects return an error and process is unreachable.
F-02An endless asynchronous loop in that same sandbox is not interrupted: the node:vm timeout only covers the synchronous part and the fallback timer never gets to fire. Verified: with a 500 ms timeout the call had not returned after 8 s. Only the supervisor stops it after 180 s without progress, and the run ends with no answer.Stability; mediumThe same process separation as F-01, terminated by signal. Test: the asynchronous loop returns the timeout error in the expected time.
F-03ensure_runner_script (py/ii-run-mode.py) downloads runner.js from GitHub Pages and runs it with Node with all the privileges of the account, checking neither integrity nor size. Up to 10.7 the code served by that origin could only act through the permission engine; now it runs outside it. No test covers the download, the 304 response, the cache or the network failure.Security (supply chain); mediumLaunch the runner with --permission (it only needs the network), cap the download size and, optionally, publish a digest next to the artifact. Test: the four download branches against a local server.
F-04runner.js is a generated artifact (npm run build:runner) that is published and that servers execute, and no test checks that it matches the code in js/, unlike zerochat.py and the bundles. It matches today [cmd]. If it falls behind, server runs use a different agent from the interface with no warning.Stability; mediumA case in test_vendor_build.js that regenerates the runner into a temporary directory and compares it. The audit procedure now lists it among the artifacts.
F-05Attachments and images stored separately (blobs) are never deleted: there is no DELETE on the blobs table in py/ee-storage.py and no deletion in the blobs store of js/storage.js. Deleting a conversation, a project or the whole history keeps its blobs, up to 50 MB each.Data and disk; mediumWhen deleting conversations, remove in the same transaction the blobs no other one references, in SQLite and in IndexedDB. Test: the blob of the only conversation using it is deleted and a shared one is kept.
F-06Leftovers from the call signature removed in M56: send_cors_headers (py/ff-server.py) still allows four X-ZeroChat-Tool-* headers that no client sends, and js/tools/README.md still describes the HMAC signature on the client. The user help described it too: help/remote-proxy.html and its translation spoke of "signed tools" and a 30 s clock skew (contributed by the Gemini review).Technical debt; medium because it affects the helpHelp fixed in this review: it now describes permissions on the server and the expiry of pending authorizations. The headers and the README remain. Test: the list of allowed headers is exactly the one the interface sends.
F-07scripts/test-runner.mjs names two files that do not exist (tests/unit/test_mcp_status.js in the mcp group and tests/test_browser_ui.js as a fallback) and silently drops missing group files. When that test was deleted, SERVICE_STATUSES in js/mcp-status.js stopped being compared with the shared contract, which only Python checks now.Technical debt; lowThe runner fails if a group file does not exist; an assertion in test_ui_mcp.js compares the statuses with the fixture.
F-08RUN_TOTAL_TIMEOUT and RUN_IDLE_SECONDS are read from environment variables that, according to the code comment and py/README.md, "only the tests use": this is production code serving the tests (AGENTS.md §2).Rule; lowTurn them into documented options of the unattended mode, which have a real use in long tasks, or patch the constants from the test.
F-09CI only uses ubuntu-latest with Node 22 and Python 3.12. The Windows paths (LogonUserW, Job Object, data file permissions) and macOS are never run, and the runner's declared minimum (Node 18) is not tested.Stability; mediumA matrix with windows-latest and macos-latest for the Python infrastructure tests, and a Node 18 job for test_run_node.js.
F-10The coordinators keep growing: js/app.js has gone from 1,020 to 1,298 lines and js/mcp.js from 1,058 to 1,233; py/ff-server.py has 1,131 and py/dd-security.py 972.Technical debt; lowSplit them when touched: the backend session out of app.js, and the JSON-RPC method dispatch of ff-server.py into one table per domain.
F-12When the day changes with the server running, current_session_token() (py/cc-environment.py) generates the new token but does not call reset_session_authorizations(), which only runs at startup (py/zz-main.py). py/README.md promises to forget them "at startup or when the token rotates" and the browser rereads the state relying on it. With --keep-server for several days, permissions granted "for this session" survive the change of day. py/test_token.py tests the token rotation, not the permissions. Contributed by the Gemini review.Security; mediumForget session authorizations in the same rotation, under the same lock. Test: with a simulated date, a session permission granted the previous day asks for confirmation again.
F-13removeConversations (js/storage.js) first deletes the IndexedDB copy and then asks the server to delete. If the server refuses (for example, because a run is in progress), the conversation disappears from the browser and stays on the server until the next synchronization, and the user gets an error about something they no longer see. Contributed by the Gemini review.Data; mediumWith the server connected, confirm the remote deletion first and only then delete the local copy. Test: a server refusal leaves the conversation in IndexedDB.
F-14The browser sandbox restores Function.prototype.constructor in a synchronous finally (js/sandbox.js), before the model's asynchronous code finishes: after the first await the block is gone. The opaque-origin iframe with no network contains it, but it is an asymmetry with the Node version. Contributed by the Gemini review.Security; lowRestore when the code's promise settles. Test: a constructor escape after an await returns an error.
F-15validate_local_tool_arguments (py/ee-mcp.py) only knows the string, integer and boolean types; an argument declared with another type would end in isinstance(value, None) and an exception, not a rejection. No local tool declares one today [cmd]. Contributed by the Gemini review.Stability; lowReject an unknown type explicitly. Test: a definition with an unsupported type returns the validation error.
F-11The repository tracks working files: todo.txt, test-results/.last-run.json and a copy of the Google verification file inside js/, identical to the one at the root.Presentation; lowRemove them from the index and add them to .gitignore.

Under the procedure, F-01 must be fixed or explicitly accepted before the next major version. Since it affects a feature that is already published, it is better not to wait for it.

6. Verdict

Infrastructure with a solid permission core and a new edge without the same protection. Moving authorization to the backend was done well: a single decision point, state in SQLite with transactions, single-use challenges, failures that propagate instead of degrading to "allow", and 38 tests that prove it. Execution in Node, by contrast, arrived in two days and left three gaps in the same area: a sandbox that does not isolate, a runner that is downloaded and executed unverified, and a generated artifact with no sync test. None affects people who use ZeroChat only from the browser; all three affect server runs, which are the main novelty of the 10.x series. A second pattern, pointed out by the Gemini review, is the life cycle: several parts only clean up on the happy path (session permissions at startup but not when the token rotates, attachments never, the local copy before the server confirms).
