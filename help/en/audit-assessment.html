Review 5: Technical level and evolution

A reasoned opinion on the technical quality of ZeroChat 10.16.0 and advice for its next stage. Written on 13 November and updated on 14 November 2026.

What this page is

The four previous reviews describe verified facts. This one is an opinion: an assessment of the technical level of ZeroChat 10.16.0 and some advice on where to take it. It rests on those reviews and on reading the code, but its conclusions are debatable and should be read that way.

The yardstick is twofold: what can be expected from a personal project maintained by one person with coding agents, and what would be demanded of a product that runs commands on its user's machine.

1. Assessment by area

AreaLevelWhy
Tests and executable rulesVery high847 tests that run in under a minute and, above all, 14 files of architecture tests that turn the rules into something that fails. It is the most distinctive trait of the project and uncommon even in professional teams. The backend is now tested on Linux, Windows and macOS. It lacks coverage measurement and a test that launches the real runner with its permissions.
Permission engineHighA single decision point on the server, transactional state, single-use challenges, commands validated subcommand by subcommand and failures that never degrade to "allow". It is designed the way someone who knows the problem would design it.
Perimeter securityHighDaily token, PAM sign-in with no dependencies, anti-SSRF on every redirect and a closed innerHTML list. In server runs, the Node process runs with restricted permissions and a credential limited to its run, and the model's JavaScript goes in a separate process with no credential. What remains are known risks: runner.js comes without a hash from the same origin as the interface, and that separate process has network access.
Frontend architectureHigh72 modules with no bundle, state in slices with mutators, persistence and DOM boundaries watched by tests, and an agent loop that runs the same in the browser and in Node thanks to adapters. Trade-off: no type analysis.
Backend architectureHighIt is still a single dependency-free file acting as HTTP server, process manager, permission engine and SQLite store, but it is now generated from 31 modules in 11 packages with real imports, no cycles, and ruff and pyright in CI, and it behaves the same imported as a package as compiled. It is the clearest structural improvement of the series.
Data modelMediumThe data lives twice (SQLite and IndexedDB) and the relationship between the two copies has been redefined several times in a week. Deletion is now consistent: the server first, and each attachment is collected when no saved message uses it. There is still no concurrency control between tabs and no server backup. It is the least settled area.
Development processHighVersioned project memory, recorded decisions, 300-line tasks, periodic audits and continuous cleanup. The findings of the previous review became tasks and were fixed the same day, each with its test. The risk lies in the pace: sixteen minor versions in seven days leave no time for real use to find the faults.
Product and user experienceMedium-highIt covers a lot and covers it well, but each series adds concepts: local and server profiles, a project per tab, three permission scopes, two execution environments. The entry curve grows faster than the help that explains it.
DocumentationHighBilingual help with its sync test, READMEs with contracts per subsystem and a decision log that lets you reconstruct the why of almost everything.

2. Overall opinion

The technical level is high, and in testing and permission discipline it is above what most projects of its size show. It is not a prototype that grew: it is a system with defined boundaries that cleans itself up and can change architecture in a week without breaking. That is hard to achieve, and harder with almost all the code written by agents.

That last point is the key to understanding it. Quality is not guaranteed by whoever writes each line, but by the set of rules that fail when broken. Where those rules exist, the code is consistent; where they have not been stated yet, the gaps appear, and they appear fast because the delivery pace is very high.

There are five underlying weaknesses, and none is about craft but about structure:

  • Static verification is partial. The backend has ruff with two rules and pyright in basic mode; the 30,000 lines of JavaScript still have no checked types, and their contracts between modules are watched only by tests.
  • Two execution environments for the same agent, with different guarantees that must be kept by hand.
  • Two copies of the data with no single rule about which one rules.
  • Dependence on a web origin it does not control (GitHub Pages under a shared domain), which now also serves code that runs on the server.
  • A single person. The project memory mitigates it very well, but nobody else has used or reviewed the system.

3. Advice on evolution

Now: test server mode as it is used

  1. Test the real runner. A test that launches runner.js with --permission and its credential, and checks what it cannot do: today the startup tests replace Node with a script.
  2. Cut the sandbox's network when possible. From Node 25 the permission model limits the network; raising the minimum for the sandbox process, or checking its version, would close the one thing it keeps.

Next: give ground to what grew fast

  1. Type checking without giving up "no bundle". JSDoc annotations and tsc --checkJs --noEmit as a sixth validation level, starting with state, storage and the agent loop. The backend has already taken that step; in JavaScript it does not change how the application is served and it catches the class of errors that only tests find today.
  2. A single rule for the data. With the server connected, SQLite rules and IndexedDB is a cache; with a version per conversation to detect that another tab saved first, instead of letting the last one win. M63 already took the first step by synchronizing headers only.
  3. Server backup. Now that history lives in ~/zerochat/storage/, a command to export and restore it is worth more than any new feature.
  4. Agent evaluations. A small, reproducible battery of tasks, run with zerochat --prompt against several local models, measuring successes, steps and context used. The current tests prove the code does what it says; none proves the agent solves tasks. No per-model tuning: the battery measures the product, it does not tweak templates.
  5. A stable channel. Keep publishing as often as wanted on a development channel and promote to stable every week or two, with a changelog. Sixteen versions in seven days are too many for someone installing from PyPI.
  6. Widen the backend's static analysis. ruff uses two rules and pyright the basic mode with four rules disabled; widen them little by little, and bring them into the npm run test levels so they do not depend only on CI.

Later: decisions about direction

  1. An origin of its own. Its own domain removes the shared-origin risk and allows real security headers, including a content policy without 'unsafe-inline' or 'unsafe-eval'.
  2. Simplify before adding. A single kind of profile, or an assistant explaining when to use each; a visible table of what works in the browser and what on the server. The next leap in quality is a new person understanding it in ten minutes.
  3. Decide the support matrix. Seven providers, three browsers, three systems and two execution environments are many combinations for one person. Declaring what is tested and what is "best effort", and removing what is not used, is a legitimate way to improve.
  4. Optional hybrid RAG. Local model servers already expose embeddings; using them when present, alongside the lexical index, would close the most cited gap without adding dependencies to the server.
  5. Keep multi-user outside. The M62 decision, one server per person, is the right one for a program acting with a system account. What would help is an official container recipe, not accounts inside the process.
  6. Find a second pair of eyes. An external review of the permission engine and of server mode, or simply two or three people using it daily, would find what neither the tests nor these audits see.

4. In one sentence

A high-level project whose greatest asset is its executable rules and whose greatest risk is its own speed: the advice is not to do more, but to spend the next series settling what the 10 series has raised.
